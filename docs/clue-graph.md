# 단서 그래프 (Clue Graph) — 한능을 "문제집"에서 "헷갈림을 고치는 기계"로

작성 2026-10-15 · 상태: 제안(사용자 결정 대기) · 시제품 `tools/proto/clue-graph-proto.mjs`

## 1. 한 줄 요약
한국사를 **문항이 아니라 「대상–단서–사실」 그래프**로 저장하고, 그 그래프에서 문제를 무한히 만들어 낸다. 사용자가 고른 **오답 선지가 어느 대상의 사실인지**까지 알기 때문에 "틀렸다"가 아니라 **"광종을 성종과 헷갈린다"**를 진단하고, 그 쌍만 집중해서 다시 낸다.

## 2. 경쟁자와 전문가가 놓친 지점
- 시중 앱(오늘한국사, 원유철의 한능검 N제, 고종훈 OX 문제집, 전한길 한능검 등)과 강의는 모두 **기출 문항·기출 선지 은행** 위에 서 있다. 콘텐츠 단위가 "문항"이라서
  1. 문항 수가 고정 — 다 풀면 끝(재방문 한계). 우리도 300문항이면 하루 10문제로 한 달이면 바닥.
  2. 오답노트가 "틀린 문항" 단위 — **왜** 틀렸는지(무엇과 혼동했는지)를 모름.
  3. 같은 혼동(광종↔성종)이 다른 문항에서 반복돼도 연결되지 않음.
- 그런데 **시험 자체가 그래프로 출제된다**: 심화 문항은 거의 다 ① 지문의 단서로 (가)를 판별 → ② 다섯 선지 중 (가)의 사실 고르기. 오답 선지는 대부분 **같은 범주 다른 대상의 진짜 사실**이다(우리 questions.js 300문항도 그렇게 썼다). 출제 구조를 그대로 데이터 구조로 가진 서비스가 없다.

## 3. 통할 거라는 근거
| 근거 | 데이터 |
|---|---|
| 개념 단위 검색이 문제집 검색보다 크고 넓다 | 네이버 월간(2026-10-15 API): 대동법 5,930 · 신간회 3,960 · 광종 3,830 · 예송논쟁 2,520 · 고려왕순서 2,270 · 균역법 2,130 · 환국 1,720 · 붕당정치 1,530 · 근우회 1,480 · 영정법 1,260 vs 한능검문제 1,190 · 한능검모의고사 410 · 한능검오답노트 60. 대상 수백 개의 롱테일 합은 "한능검 문제"류를 크게 넘는다 |
| 우리 실제 유입도 개념 페이지로 들어온다 | Web Analytics 10/12~15: 외부 유입 첫 페이지가 /summary/, /era/three/, /era/goryeo/ (블로그 '헷갈리는 것만' 글 경유) |
| 헷갈림이 핵심 고통 | 블로그·정리 페이지에 쓴 "헷갈림 주의" 항목이 그대로 오답 패턴(태조/광종/성종, 을미/을사/정미의병, 영정법/대동법/균역법) |
| 콘텐츠 규모가 바뀐다 | 시제품: 대상 5·단서 21·사실 17 → 선지 순서 무시하고도 **서로 다른 문항 5,106개, 선지 오류 0건**. 300문항 전체보다 고려 왕 5명이 더 많다 |
| 재방문 구조와 맞물림 | 매일 알림(/today/)이 데려와도 문항이 반복되면 이탈. 무한·개인화 출제가 알림의 가치를 만든다 |
| 비용 0 | 정적 JS에서 생성, 서버·API 없음. 저작권: 대상·사실·단서는 역사적 사실(자체 서술), 기출 지문·선지를 옮기지 않음 |

## 4. 가장 강한 반박과 답
1. **"템플릿 문항은 진짜 시험(사료형)보다 쉽고 지루하다."** — 가장 아픈 반박. 실제 시험은 단서가 문장·그림 속에 숨어 있다. → 답: 유형을 두 단계로 나눈다. A(단서→대상)는 판별 훈련, B(단서→사실)는 선지 판단 훈련. 단서는 시험 지문에 실제로 등장하는 '결정적 표현'(쌍기, 노비안검법)으로 쓴다. 그래도 지문형 감각은 부족하므로 **대상마다 직접 쓴 짧은 사료풍 지문 1~2개**를 그래프에 붙여 C 유형으로 쓴다(2단계). 기존 300문항은 '실전형'으로 유지. → **살아남음(조건부: C 유형 필요)**
2. **"사실 하나가 틀리면 수십 문항이 동시에 틀린다."** — 맞다, 오류가 증폭된다. → 답: 사실은 원자 단위로 한 번만 쓰고 출처 메모를 단다. `only`(그 대상에게만 해당) 표시가 없는 사실은 오답 선지로 절대 쓰지 않는다(시제품에서 자동 검증). 같은 사실이 두 대상에 걸리면(6조 직계제=태종·세조) 테스트가 실패하게 만든다. 제보 1건이 그래프 1곳을 고치면 모든 파생 문항이 함께 고쳐진다 — 오히려 고정 문항보다 유지보수가 쉽다. → **살아남음**
3. **"이미 누가 하고 있다."** — 오늘한국사의 '키워드 매칭'이 가장 가깝다. 하지만 기출 선지를 키워드와 짝짓는 방식이고, 선택한 오답의 **출처 대상**으로 혼동 쌍을 진단·가중 출제하는 기능은 공개 설명에서 확인되지 않았다. 다만 모든 경쟁 앱을 써 본 것은 아니다. → **부분 생존: 구현 전 오늘한국사 직접 설치 확인 1회 필요**
4. **"개념 검색은 나무위키·우리역사넷이 다 가져간다."** — 신규 도메인이 '대동법' 단독 키워드 1페이지에 가기는 어렵다. → 답: 검색 유입은 보너스로만 본다. 노리는 건 롱테일 비교형("광종 성종 차이", "을미의병 을사의병 정미의병")과 시험 목적 검색자. 핵심 가치는 학습 효과·재방문. → **살아남음(검색 효과는 불확실로 표기)**
5. **"하루 10문제로는 혼동을 진단할 데이터가 안 쌓인다."** — 통계적으로는 맞다. → 답: 진단에 통계가 필요 없다. 오답 1번 = 그 선지의 출처 대상 1개 = 혼동 쌍 1개가 **즉시** 확정된다. 사전 혼동 쌍(같은 범주·인접 시기)으로 첫날부터 의미 있는 오답 선지를 고른다. → **살아남음**
6. **"그래프 작성 분량이 너무 크다."** — 대상 ~200 × 단서 4~5 × 사실 3~5 = 사실 약 800개. 한 번에는 무리. → 답: 혼동이 가장 많은 영역부터(고려 전기 왕, 조선 전기 왕, 조선 후기 수취 제도, 의병, 일제 통치기, 현대 정부) 약 40개 대상으로 MVP. 기존 300문항·핵심 정리 표에서 사실을 옮겨 오면 절반은 이미 있다. → **살아남음(단계적)**

**결론: 살아남음.** 조건 두 가지 — (1) MVP에 사료풍 지문(C 유형)을 일부라도 넣을 것, (2) 만들기 전에 오늘한국사를 직접 확인해 차별점을 재확인할 것.

## 5. 만드는 방법 (구현 명세)

### 5.1 데이터 `assets/graph/*.js`
```js
// 대상
{ id: 'gwangjong', era: 'goryeo', kind: 'king', name: '광종', order: 4,  // 같은 kind 안 시간 순서
  clues: ['쌍기', '노비안검법', '광덕·준풍', '백관의 공복'],                 // 지문 속 결정적 표현
  facts: [{ id: 'gj-1', t: '노비안검법을 실시하였다.', only: true, src: '고려사 세가 광종 7년' }, ...],
  passages: ['○○ 7년, 노비를 조사하여 옳고 그름을 가리게 하니…'],          // 직접 쓴 사료풍 지문(C 유형)
  rivals: ['seongjong', 'taejo'] }                                          // 사전 혼동 상대
```
- kind: king(왕) · policy(제도) · event(사건) · person(인물) · group(단체) · heritage(문화유산)
- 검증 테스트(`tests/graph.test.mjs`): 사실 문장 전역 중복 금지, `only:true` 사실의 핵심어가 다른 대상의 단서·사실과 겹치면 경고, 대상마다 단서 ≥3·only 사실 ≥2, rivals는 같은 kind, 조사 처리(받침에 따라 와/과·을/를) 함수 단위 테스트

### 5.2 문항 생성 `assets/graph-engine.js`
- A `clueToEntity(id, rand)` — 단서 2개 → 같은 kind 5지선다
- B `clueToFact(id, rand, weights)` — 단서 1개 → 정답 사실 1 + 오답 4(혼동 가중치 높은 상대의 only 사실 우선, 대상당 1개)
- C `passageToFact(id, rand, weights)` — 사료풍 지문 → 사실 고르기(시험과 같은 형식)
- D `order(kind, era, rand)` — 같은 kind 4개 시간 순서 배열(order 필드)
- 모든 문항에 `{ answerEntity, distractorOf: {선지: 대상id} }` 메타 → 채점 시 혼동 쌍 기록
- 날짜 시드(기존 dailyIds와 같은 방식)로 '오늘의 10문제'에 B·C 유형을 섞어 넣는다(기존 고정 문항 5 + 그래프 5부터 시작)

### 5.3 기록 `localStorage hanneung:v1.confuse`
`{ "gwangjong|seongjong": { n: 3, last: '2026-10-20' } }` — 오답 시 +1, 같은 쌍에서 정답 2연속이면 −1. 서버 전송 없음.

### 5.4 화면
1. **결과 화면 "헷갈림 지도"**: "광종 ↔ 성종 3번", "을사의병 ↔ 정미의병 2번" + [이 둘만 5문제] 버튼 → `#/pair/gwangjong|seongjong`
2. **쌍 집중 퀴즈**: 두 대상의 단서·사실만으로 B/D 유형 5문항, 끝나면 차이표(두 대상 나란히)
3. **오답노트 상단**: "가장 많이 헷갈린 쌍 TOP 3"
4. 공유 문구: "나는 광종이랑 성종을 3번 헷갈림 — 너는?" (공유 버튼 재사용)

### 5.5 정적 페이지 (검색 롱테일)
- `/vs/<a>-<b>/` 쌍 비교 페이지: "광종 성종 차이 — 한능검 헷갈리는 왕 비교"(차이표 + 단서 + 바로 풀기). MVP 20쌍
- `/k/<id>/` 대상 페이지: "광종 — 시험에 나오는 단서 4개와 업적"(+ 헷갈리는 상대 링크). MVP 40개
- sitemap 추가, 각 페이지 하단에 매일 알림 카드(이미 있음)

### 5.6 측정·판정
- 경로 기반: `/vs/*`·`/k/*` 페이지뷰(검색 유입), `/today/`(알림 재방문) — `scripts/metrics.mjs`에 집계 추가
- 해시 라우트 `#/pair/…` 사용량은 지금 구조로는 측정 불가 → 쌍 퀴즈 진입을 `/pair/?p=…` 경로로 만들어 페이지뷰로 셈
- **성공 기준(배포 후 3주)**: 쌍 비교·대상 페이지 외부 유입이 /summary/를 넘음, /today/ 일평균 ≥2, 쌍 퀴즈 진입 주 ≥20
- **중단 기준**: 3주 뒤 /vs·/k 외부 유입 합계 < 30이고 쌍 퀴즈 진입 < 10 → 그래프 확장 중단, 고정 문항 방식으로 복귀

### 5.7 MVP 범위와 순서 (약 2~3회 작업 분량)
1. 그래프 스키마·검증 테스트·조사 처리 + 고려 전기 왕 8(태조~숙종·예종) — 시제품 확장
2. 조선 전기 왕 6(태조~성종), 수취 제도 3(영정법·대동법·균역법), 의병 3, 일제 통치기 3, 현대 정부 8 → 대상 약 31 + 사료풍 지문 대상당 1
3. 생성기 A·B·C·D + 혼동 기록 + 결과 화면 헷갈림 지도 + 쌍 집중 퀴즈
4. /vs/ 20쌍, /k/ 31개 정적 페이지 + sitemap + 메트릭
5. 단위·E2E·운영 검증 → 배포 → PROJECT_STATE 사이클 기록

## 6. 남은 불확실성 (정직하게)
- 경쟁 앱 전수 확인은 안 했다(오늘한국사 직접 확인 필요)
- 템플릿 B 유형이 실제 점수 향상에 얼마나 기여하는지 근거 없음 → 사용자 정답률 변화로 측정
- 검색 유입 효과는 신규 도메인이라 불확실
